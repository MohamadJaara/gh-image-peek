# Desktop Chrome alongside Firefox

Research date: 2026-11-01. Investigation only: no implementation, dependency changes, browser installation, test execution, or commits. **Chrome compatibility has not been tested.** Official sources below were checked on this date; recommendations are engineering judgments, not verified outcomes.

## Repository baseline

Inspected `README.md`, `extension/manifest.json`, `extension/content.js`, `extension/viewer.css`, `playwright.config.js`, the test fixtures, and existing research notes. No on-disk `AGENTS.md` was found in the repository or its ancestors; the supplied GitHub CLI instructions apply.

The current extension is MV3, with static JS/CSS content scripts matching `https://github.com/*` at `document_idle`. The viewer uses DOM/CSS and ordinary image elements; it calls no `browser.*`/`chrome.*` extension APIs and has no background process. Manifest icons are one SVG at 48/96 sizes. Firefox metadata contains the existing ID, desktop minimum 140, Android minimum 142, and `data_collection_permissions.required: ["none"]`. The local uncommitted Gecko `update_url` points to `https://github.com/MohamadJaara/gh-image-peek/releases/latest/download/updates.json`.

Tests currently configure only Playwright Firefox, with `@playwright/test` pinned to 1.64.1. Fixtures use `page.addScriptTag`/`page.addStyleTag` after navigation; they do not install the extension. Existing local changes, including the manifest and `github-distribution.md`, were left untouched.

## Shared source and generated manifests

**Recommendation:** keep one `content.js` and `viewer.css`; add a small packaging step that copies them into separate Firefox/Chrome output directories and generates a root `manifest.json` for each. Share name/version/description/MV3/content-script fields; apply explicit browser/distribution overlays. This avoids maintaining two viewer implementations. Separate outputs are a maintenance choice, not a browser requirement; MDN documents browser-specific manifest differences and ZIP packages with the manifest at their root. [MDN: cross-browser extensions](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/Build_a_cross_browser_extension#manifest_keys)

- **Firefox output:** preserve the current `gecko` and `gecko_android` metadata, including ID, version floors, and data declaration. Firefox requires an explicit ID for MV3 signing. Retain the local Gecko update URL for a self-distributed Firefox artifact; an AMO-distributed artifact needs its own distribution configuration. [MDN: browser-specific settings](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/manifest.json/browser_specific_settings)
- **Chrome output:** omit `browser_specific_settings` for clarity. MDN explicitly says Chrome ignores it if present, so removing it is not itself the compatibility fix. Its Firefox ID, minimums, consent declaration, and nested update URL do not configure Chrome. Set a separate `minimum_chrome_version` only after choosing and validating a Chrome support floor; Firefox's version number does not establish one. [MDN: Chrome handling](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/manifest.json/browser_specific_settings#chrome_properties), [Chrome manifest reference](https://developer.chrome.com/docs/extensions/reference/manifest)

## Icons and permissions

**Required packaging change:** Chrome manifest icons do not support SVG or WebP. PNG is recommended, although other supported raster formats can serve manifest icons. Separately, the Chrome Web Store requires a **128×128 PNG** in the ZIP. Generate real PNG exports from the existing artwork; recommend 16/32/48/128 sizes, with 48 for extension management and 128 for installation/store use. Firefox can retain SVG or use raster icons. This limitation concerns extension icons, not the viewer's ability to display SVG screenshots. [Chrome manifest icons](https://developer.chrome.com/docs/extensions/reference/manifest/icons), [Chrome Web Store image requirements](https://developer.chrome.com/docs/webstore/images#extension-icon), [MDN: Firefox SVG icons](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/manifest.json/icons#svg)

Keep the static `https://github.com/*` declaration. Chrome permits manifest-declared injection without duplicate `host_permissions`; `scripting`, `activeTab`, and `tabs` are unnecessary for this design. However, **no extra API permissions does not mean no site access**: `content_scripts.matches` grants injection access and can trigger a permission warning. Keep the GitHub scope visible in privacy/install documentation. [Chrome: declaring permissions](https://developer.chrome.com/docs/extensions/develop/concepts/declare-permissions)

**No service worker, background script, or extension-API polyfill is indicated by the current source.** Chrome lists `background` as optional and supports statically registered JS/CSS. A namespace/API polyfill would have nothing to adapt here; it does not solve DOM/CSS differences. Reassess only if extension APIs are introduced. [Chrome manifest reference](https://developer.chrome.com/docs/extensions/reference/manifest), [Chrome content scripts](https://developer.chrome.com/docs/extensions/develop/concepts/content-scripts), [MDN: API polyfills](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/Build_a_cross_browser_extension#the_webextension_browser_api_polyfill)

## Isolation and GitHub image-diff frames

Content scripts default to an **isolated JavaScript world**. They share the document with the page, enabling this viewer's DOM listeners and mutations, but cannot directly read GitHub's page-world variables or assume patches to JavaScript globals affect GitHub's code. Isolation does not encapsulate the injected DOM/CSS from the page. Retain the DOM/event approach; do not switch to `MAIN` merely to add Chrome. [Chrome: isolated worlds](https://developer.chrome.com/docs/extensions/develop/concepts/content-scripts#work_in_isolated_worlds), [MDN: execution worlds](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/manifest.json/content_scripts#world)

The README records rich image comparisons inside `render.githubusercontent.com` iframes; their current live markup was not re-verified. Given that embedding, the GitHub-only top-level script cannot inspect the cross-origin document or capture its internal clicks. `all_frames: true` alone would not help: frame URLs must still match. Supporting those frames would require deliberate additional matching/injection and frame-aware behavior/communication; the current PR-path check and gallery assume a GitHub PR document. Keep this limitation for the smallest migration. [MDN: same-origin restrictions](https://developer.mozilla.org/en-US/docs/Web/Security/Defenses/Same-origin_policy#cross-origin_script_api_access), [Chrome: frame matching](https://developer.chrome.com/docs/extensions/develop/concepts/content-scripts#specify_frames)

Displaying an external image in an ordinary `<img>` is different from reading an iframe's DOM: cross-origin image embedding is generally allowed. That distinction does not guarantee every private/expired image URL will load. [MDN: cross-origin embedding](https://developer.mozilla.org/en-US/docs/Web/Security/Defenses/Same-origin_policy#cross-origin_network_access)

## Development installation versus distribution

For Chrome development, extract the Chrome artifact, open `chrome://extensions`, enable **Developer mode**, and choose **Load unpacked** on the directory containing its generated manifest. Reload the extension after source changes and refresh the GitHub tab. A downloadable ZIP can support this manual developer workflow; it is not a direct consumer installation/update mechanism. [Chrome: Load unpacked and reload](https://developer.chrome.com/docs/extensions/get-started/tutorial/hello-world#load_an_unpacked_extension)

For ordinary consumer distribution, use the **Chrome Web Store**, which hosts/signs extensions for direct installation; publishing requires a separate ZIP submission and review process. A GitHub release or locally signed CRX does not automatically become installable for consumer Windows/macOS users: self-hosted installation there requires enterprise policies. Linux additionally permits manual installation of off-store packed extensions. Packing/signing a CRX alone does not bypass these restrictions. [Chrome distribution rules](https://developer.chrome.com/docs/extensions/how-to/distribute), [Chrome Web Store submission](https://developer.chrome.com/docs/webstore/publish/)

Firefox's corresponding permanent-release path requires **Mozilla signing**, including for unlisted/self-distributed XPIs. Mozilla signing does not authorize a Chrome package. [Mozilla signing and distribution](https://extensionworkshop.com/documentation/publish/signing-and-distribution-overview/)

Update mechanisms are separate:

- **Firefox self-distribution:** nested `browser_specific_settings.gecko.update_url` identifies an HTTPS **JSON** update manifest keyed by Firefox add-on ID and linking to XPI updates. Merely adding the local GitHub URL does not create that file, signed XPIs, or a working update pipeline. AMO-hosted versions receive updates through AMO. [Mozilla update format](https://extensionworkshop.com/documentation/manage/updating-your-extension/)
- **Chrome Web Store:** publish subsequent versions through the store's update workflow; recommend omitting a self-hosted update URL from this artifact. [Chrome store updates](https://developer.chrome.com/docs/webstore/update), [Chrome manifest reference](https://developer.chrome.com/docs/extensions/reference/manifest)
- **Chrome self-hosting, where permitted:** uses a **top-level** `update_url` returning an **XML** update manifest with Chrome extension ID, version, and CRX URL. Updates must use the same signing key. Firefox's `updates.json`, XPI, and Gecko ID cannot be reused as that protocol. [Chrome self-hosted updates](https://developer.chrome.com/docs/extensions/how-to/distribute/host-on-linux#update)

It would still bypass manifest parsing, static injection, isolated-world execution, permissions, icons, installation, and updates. Playwright's bundled browsers also are not proof of the exact supported consumer releases; Playwright Firefox relies on patches and does not automate branded Firefox. [Playwright browser support](https://playwright.dev/docs/browsers)
2. **Actual extension-loading smoke test:** use Playwright's bundled Chromium with `launchPersistentContext`, an isolated test profile, and the extension-loading arguments, pointed at the **generated Chrome artifact**. Use `channel: "chromium"` for supported headless extension testing, or run headed. Visit a matching URL and assert the viewer appears without `addScriptTag`/`addStyleTag`. Do **not** copy the documentation's service-worker wait: this extension has no worker. Playwright currently documents extension support only in Chromium persistent contexts. [Playwright extension testing](https://playwright.dev/docs/chrome-extensions)
3. **Consumer-browser smoke tests:** manually load the generated artifact in current stable desktop Chrome and the Firefox artifact in Firefox; verify real GitHub PRs, same-origin previews, unchanged cross-origin exclusions, SPA entry, focus, private-image loading, and physical gestures. Test production installation/update separately once a distribution channel exists. No such checks were performed for this investigation.

The official announcements retain the flags for Chromium/Chrome for Testing; Playwright recommends its bundled Chromium. Do not assume adding `channel: "chrome"` to the extension fixture will work. ## Ctrl-wheel and pinch boundaries

The current listener uses `{ passive: false }` and cancels only cancelable Ctrl-wheel events directly targeting the loaded image. Retain that bounded behavior and the buttons/keyboard alternatives. Wheel and trackpad zoom can produce `wheel` events with `ctrlKey: true`, but some event sequences contain non-cancelable events. Delivery, delta units, OS/browser settings, and gesture targeting need real-device validation; matching a synthetic Ctrl-wheel event does not prove native pinch or browser-zoom interception works. [MDN: wheel events](https://developer.mozilla.org/en-US/docs/Web/API/Element/wheel_event)

The fitted multi-image stage currently uses `touch-action: pan-y pinch-zoom`; other cases permit native gestures. `pinch-zoom` permits browser page zoom, not custom two-pointer image scaling. Do not promise general trackpad/touchscreen pinch-to-image zoom, OS gesture suppression, or equivalent behavior across platforms. Native touchscreen pinch remains browser-controlled in this design. [MDN: touch-action](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/touch-action)

## Smallest recommended migration

Generate two browser artifacts from shared JS/CSS, export Chrome PNG icons, preserve Firefox metadata in its own artifact, and keep the current scope and controls. Add Chromium DOM coverage plus one actual extension-loading smoke test, then manually verify current stable desktop Chrome/Firefox and physical gestures before claiming compatibility. Start Chrome development with Load unpacked; choose Chrome Web Store distribution for normal consumers when ready. No new runtime dependency, worker, polyfill, broader host access, iframe feature, or custom pinch implementation is justified solely by adding desktop Chrome.
